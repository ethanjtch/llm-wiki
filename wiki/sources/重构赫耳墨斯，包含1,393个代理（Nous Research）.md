## 核心论点
**自动化最大的红利不是把已有工作做快，而是让长期被机会成本否决的工作重新变得可行。** Hermes（Nous Research 的开源代理）的百万行技术债清理被反复推迟了很多个月，因为"把工程师从功能和 bug 修复上抽走"这件事永远无法被证明合理。2026-09-02 作者让常驻 Hermes 代理执行清理：主运行约 **19 个活跃小时、派出 1,393 个子代理、峰值 218 个并发**，合并后非测试 Python 代码减少 **34.4%**。模型花费约 **$19,300**（含后续会话约 $25k，不含人工评审），而人工估算为 **$150k–$1.8M / 2 个月–2 年**——约 **1% 的成本与 1% 的时间**。

第二个论点同样重要：**规模化并不消除最后一公里的人类评审**。既有测试全绿的情况下仍漏掉两类真实回归，最后靠两轮社区人工评审 + 合并后追加修复收尾。

## 要点摘录

### 任务：一份"不许找借口"的目标
> *我希望有一套大规模简化的 PR 集合……我希望代码行数大幅下降，至少整体下降 30%。我希望拆分 god files……统一可复用的辅助函数……减少层层嵌套的 if-else……清理并移除冗余代码。我希望所有工作都完成。不要找借口。不要等待我的决定。完成后向我提交一个或一组 PR。*

作者用 `/goal` 给它设定**持续目标**，让代理在"本来会停下"的时候继续推进。任务起点：仓库超过 100 万行非测试 Python，`gateway/run.py` 单文件 34,847 行。

### 编排结构
- 协调者**测量代码库并划分为 36 个互不重叠的组**，用目标 + 累积技能自动撰写任务书——作者不需要逐个向工人交代。
- 工人使用 **git worktree**（独立检出，互不覆盖文件）；任务书明确"要简化的代码、要保留的接口、提交前必须通过的检查"。
- 部分工人继续向下委托，**委托树达三层**；最顶层的代理只做协调、不编辑源码：写任务与脚本、读工人报告、合并分支、跑检查。
- 全部代理由**一台 i7 / 64GB 的桌面机上的单个 Python 进程**协调；工具在本地子进程运行，推理远程完成（Claude Fable 5.1）。

### 验证机制（关键约束）
- 用**冻结的基线（frozen baseline）**：集成工人改动时，把失败与基线对比，判断失败是否为既有问题。
- 接口逐项核对：工具的 **JSON schema 必须完全一致**；CLI 命令的 **`--help` 输出逐字节比较**。
- 每个验证通过的步骤都要 **commit**（可回滚、可交接）。

### 一次真实故障
约 50 分钟时，供应商的认证令牌过期，连锁失败直接杀死运行。**工人的 commit 与任务书存活下来**。作者用另一个 Hermes 会话诊断故障、准备好交接材料，交给恢复后的会话；Hermes 派工人回头检查已保存的改动、修完未完成的抽取，继续跑完。

### 回归与人类评审（不可省的一环）
- 审阅者发现工人删除了"**仓库内没有调用者、但外部插件会 import**"的公共名称。
- 对 `suppress()` 调用的自动重写**在约 65 处改变了异常处理语义**。
- 这些都是**既有测试遗漏的真实回归**；合并前经两轮社区评审修复，合并后仍有追加修复。

### 前后对比

| 指标 | 之前 | 之后 |
|---|---|---|
| 非测试 Python 行数（全部目录） | 1,063,826 | 698,363 |
| 超过 5,000 行的文件 | 37 | 6 |
| 超过 300 行的函数 | 192 | 2 |
| 最长的 `if/elif` 链 | 92 个分支 | 9 |
| `gateway/run.py` | 34,847 行 | 5,512 |

具体手法：把 `gateway/run.py` 的消息分发、流式处理、RPC 与生命周期拆成模块；合并重复辅助函数；用**调度表（dispatch table）**替换基于长名字的 `if/elif` 链。

### 附带测量：代码对代理是否也更好读
模拟在两个版本中查找同样的 4,000 个符号（先搜定义，读 60 行窗口，定义超窗则按 2,000 行窗口续读）：

- 平均每次查找返回的 token：**2,218 → 993**
- 需要第二次读取窗口的查找：**628 → 184**
- **但中位数反而上升**：注释与 docstring 变少，固定行窗口里代码更密。

作者明确这只是**查找成本**，没有测量代理完成工程任务的成功率。

### 代价（作者主动列出）
拆分增加了模块数量与导入依赖，部分入口点导入更慢；重构让**单个部件**更易读，但并未解决它们之间的耦合；仍有 6 个文件超过 5,000 行。

### 教训：规模反过来暴露 harness 的缺陷
- 不同 worktree 里的工人启动了约 **30 个 Pyright（Python 语言服务器）副本，吃掉约 8.7GB**；后续改为共享一个服务器，并加"活体检查"确认诊断仍来自各 worktree。
- 减少重复的 HTTP transport；修掉让已完成代理滞留内存的引用。
- **仓库规则被改写**：针对文件大小、函数复杂度、新行为应归属何处（按区域拆分，让工人在需要时拿到相关规则）写入指导；新增"标记被删除的公共名称"的检查与测试供审阅。

### 自我改进：技能累积
`hermes-agent-dev` 技能由日常协作长出——"我们制定出一个程序或纠正一个错误时，Hermes 自动注意到并保存可复用的经验"，逐渐积累出如何准备 PR、避免哪些捷径、如何验证改动的指令。技能是**可读的 Markdown 文档**（必要时附参考文件与脚本），代理在工作过程中自行编写与修订，也可分发给所有工程师装进各自的 Hermes 使用。本次重构后，技能被自动更新以包含这次的经验。

> *这是一个绝佳的例子，说明 Hermes 如何成为团队的超能力：通过 Hermes 解决问题，让它记录你学到的东西，并让这份经验可用于下一个任务、下一位工程师。*
