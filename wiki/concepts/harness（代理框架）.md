## 一句话定义
围绕模型搭建的脚手架（提示策略、专用代理、工具、文件工件、编排循环的统称）；决定长任务成败的往往不是模型本身，而是 harness 是否补偿了模型的已知弱点。中文常译"框架"，直译"管理工具/工具带"。

## 展开解释
- **为什么需要 harness**：模型在长任务上存在系统性弱点——一次性做得太多、过早宣布完成、未测试就标完成、接近上下文极限就收尾、对自己的作品盲目乐观。[[长期运行代理的有效管理工具（Anthropic）]] 与 [[长期运行应用开发的框架设计（Anthropic）]] 证明：给这些弱点配专门的"外骨骼"，能从"做不出生产级应用"变成"数小时自主构建可玩应用"。
- **组成部件**：初始化/规划代理（铺环境、拆解任务）＋ 执行代理（增量推进）＋ 评审代理（独立验证）＋ 文件工件（进度文件、功能清单、验收契约）＋ 版本控制（git）＋ 浏览器自动化（Puppeteer/Playwright MCP）。
- **核心机制**
  - 任务分解：初始化代理把需求拆成逐条可验收的 feature（claude.ai 克隆 = 200+ 条），一次只做一个；
  - 跨会话上下文：进度文件 + git 历史 + 功能列表，让新会话快速"从零上手"；
  - 干净状态：每个会话结束留下可合并主分支的代码；
  - 独立评估：评审代理以用户身份点测应用，抵消[[自我评估偏差]]；
  - 端到端可验证：浏览器自动化把"做完"变成可检验事实。
- **承重与简化**：harness 的每个组件都编码了一个"模型自己做不到"的假设，会随模型变强而过时。维护纪律是**逐一移除组件做对照实验**，找出真正承重的部分（planner 删除后生成器 under-scope、评估器只在超出模型 solo 能力时值回票价）。模型升级（如 Opus 4.6）后常可拆掉 sprint、reset 等脚手架。
- **上限不是模型而是评估**：多代理极其昂贵（6 小时/$200 vs 单代理 20 分钟/$9），评估器要能被调教出可靠的品味/口味才值得——这正是 [[可验证性]] 问题的工程化回答。
- **规模极端下的 harness（Hermes 实证）**：把同一套思路推到 **1,393 个子代理、19 活跃小时、峰值 218 并发**（[[重构赫耳墨斯，包含1,393个代理（Nous Research）]]）后，新增的承重件是**隔离**（工人各用一份 git worktree）与**契约**（必须保留的接口、JSON schema 完全一致、`--help` 逐字节可比、每步验证后 commit）；协调者只写任务书与集成，不编辑源码（[[代理编排树]]）。
  - **harness 自己也会成为瓶颈**：规模一上去，暴露的缺陷在 harness 而非模型——约 30 份语言服务器副本吃掉 8.7GB、重复的 HTTP transport、让已完成代理滞留内存的引用。"做减法"与"加复杂度"并不矛盾：**给同一任务做减法，为更大的任务做加法**。
  - **harness 与技能的分工**：harness 是**任务内**脚手架（随模型变强变薄），[[技能累积|技能]]是**跨任务**的程序记忆（随使用变厚）——一个是外骨骼，一个是肌肉记忆。

## 反例 / 边界
- 单代理 + 强模型不等于 harness：没有分解和验证的外壳，核心玩法照样坏（solo run）。
- harness 不是万灵药：模型的产品直觉缺口（工作流无引导）、感知缺口（看不到 native alert、听不到音乐）仍封顶效果。
- 千级代理不是默认配置：分工粒度应是**任务规模的函数**，小任务上开千级代理只放大成本与故障面（令牌过期一次就足以杀死整个运行）。
