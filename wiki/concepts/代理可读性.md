## 一句话定义
代码库"方便人类导航"与"方便代理导航"之间的关系。两者高度相关但**不是同一件事**——把 god file 拆小可省 token，却也可能让代理需要跨文件追调用链。它可以用"代理查找一个符号要花多少 token"来测量。

## 展开解释
- **测量方法**（[[重构赫耳墨斯，包含1,393个代理（Nous Research）]] 的附带实验）：在两个版本（重构前 / 后）查找同样的 4,000 个符号——先搜定义、读 60 行窗口，若定义超出窗口则按 2,000 行窗口续读。
- **结果**：
  - 平均每次查找的 token：**2,218 → 993**（约降 55%）
  - 需要第二次读取窗口的查找：**628 → 184**（约降 71%）
  - **中位数反而上升**：注释与 docstring 变少后，固定行窗口里代码更密。
- **解读**：代价集中在**超大定义**上。少数几万 token 才能读完的函数消失后，平均值被大幅拉低；而"每个定义都更短"并不成立——密度上升抵消了部分收益。对代理而言，**长函数 / god file 是最贵的结构**（每次误入都要付整段读取），而"文件更小"只是达成本身。
- **拆分的对价**（作者主动列出）：模块数与导入依赖增加、部分入口点导入更慢；重构让单个部件更易读，却没有解决部件之间的耦合；仍有 6 个文件超过 5,000 行。
- **为什么这件事重要**：在代理参与的代码库里，**可读性是一种基础设施**。它决定了代理每次任务要烧多少 token、要读多少上下文，也就间接决定了自动化的单位成本。这使得"重构"从审美问题变成 [[被推迟工作的经济学]] 里的投资问题。
- **与 harness 的关系**：[[harness（代理框架）]] 通常指任务内的脚手架；代码库的结构、任务书、检查规则、语言服务器共享则是**代理所处的环境**。环境设计（把文件大小、函数复杂度、新行为归属写进分区规则）是与 harness 同源的另一种工程。

## 反例 / 边界
- 文中明确：**测得的是查找成本，不是工程任务成功率**。省 token ≠ 更容易把事情做对；拆分引入的跨文件追踪成本没有被这个指标覆盖。
- 中位数上升本身是反例：把"文件变小"当作单一目标会得到混合结果。
- 注释与 docstring 减少会提高代码密度——对代理是双刃（同窗口信息更多），对人类读者未必是好事。
