## 一句话定义
让 LLM 在原始来源与用户之间**增量构建并持续维护一个持久、互联的 markdown wiki**，而非在每次查询时从原始文档临时检索（RAG）。知识"编译一次并持续保鲜"，随每个新来源和每次问答**复利增长**。出处：[[大语言模型维基（Karpathy）]]。

## 展开解释
- **为什么不用 RAG**：RAG 每次查询都从源头重新拼装碎片、无积累；综合五份文档的问题要反复现场检索。wiki 模式的交叉引用、矛盾标记、综合结论**已提前编好**，查询只是读取成品。
- **三层分工**
  - 原始来源（不可变，LLM 只读）→ 真相源头；
  - wiki 层（LLM 全权写）→ 摘要/实体/概念/综合页 + 交叉引用；
  - schema 层（AGENTS.md / CLAUDE.md，人与 LLM 共演化）→ 约定结构与工作流，**把 LLM 从通用聊天机器人变成有纪律的维护者**。
- **元层面**：本模式自己就是"用 LLM 管理 LLM 产出的知识"——首页、概念页、来源页形成自我描述的闭环。
- **工作流三件套**：Ingest（读源→讨论→写摘要→更新相关页→记日志）、Query（先读 index 再下钻，好答案归档回 wiki）、Lint（找矛盾/过时/孤儿页/缺页概念/交叉引用缺失）。
- **规模信号**：index.md 目录足以支撑中等规模（~100 来源、数百页），暂不需要 embedding 基建；可配本地搜索（qmd）或自写脚本。
- **为什么能持续**：知识库维护的瓶颈是"记账"而非思考；LLM 不无聊、不忘更新交叉引用、一次可改 15 页，维护成本趋近零。
- **思想谱系**：Memex（Bush，1945）→ [[常青笔记]]（Matuschak/Ango）→ LLM Wiki 模式。常青笔记的"想法对象化 + 红链面包屑"与 wiki 的"页 + 待建页"一脉相承；[[涌现式笔记法]] 的"结构从连接中涌现"是 wiki 模式的笔记学前提；[[文件优先]] 是它的存储前提（LLM 写的必须是可控制的文件）。
- **最大的正面争论：维护者是谁**——Steph Ango 明确拒绝用 LLM 自动化笔记维护（[[我如何使用 Obsidian（Steph Ango）]]："我享受这个过程，维护帮助我理解自己的模式"）；Karpathy 把全部 bookkeeping 交给 LLM。本文库的裁决：**记账可外包、理解不外包**（见 [[认知外包]]）——人保留来源策展与提问方向，模型承担全部书写与保鲜，schema 层（AGENTS.md）是双方的契约。
- **与 [[Agent]] 的关系**：wiki 模式是"LLM as persistent worker"的一种知识管理实现——LLM 承担长期维护性劳动；对比 [[长期运行代理的工程实践]] 里靠 [[harness（代理框架）]]（进度文件、工件交接、评审回路）构造的跨会话一致性，wiki 用文件结构与日志实现同类"跨上下文不被遗忘"。Hermes 的 [[技能累积]] 则给出第三种实现：把维护经验固化成可复用的程序记忆。

## 反例 / 边界
- **不适合高频、强时效的查询场景**：wiki 有信息滞后，最新数据永远在 raw 里，需靠 Ingest 流程补全。
- **依赖用户策展**：人必须把来源放进 raw、给出方向；无人投放则 wiki 停摆。
- **依赖 schema 纪律**：没有 AGENTS.md 约定，LLM 会退回"临时检索+生成答案"的 RAG 行为，模式失效。
- **仅文本最优**：图片需额外工作流（本地下载、分步看图），非文本素材成本高。
